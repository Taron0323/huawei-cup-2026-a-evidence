## 1. 秒懂核心：用现实生活大白话看懂这道题

别被题目里的 NPU、Cube、Vector、Pipe、DDR 这些专有名词吓住。我们可以把整道题想象成**一个加工厂车间的生产调度问题**：

```
+---------------------------------------------------------------------------------+
|                                 远郊大仓库 (DDR)                                  |
|   - 空间无限大，但进出只有一条单车道乡村公路（总带宽固定 60 字节/周期，所有车核共享）|
+---------------------------------------------------------------------------------+
                         ▲                         ▲
                         │ 搬入(COPY_IN)           │ 搬出(COPY_OUT)
                         ▼                         ▼
+------------------------------------+   +------------------------------------+
|         0 号工人工位 (Core 0)        |   |         1 号工人工位 (Core 1)        |
|  [工作台 L1 (512KB)] [工具盒 UB(128KB)] |   |  [工作台 L1 (512KB)] [工具盒 UB(128KB)] |
|  - 算盘大师傅: Cube (算矩阵，极快)    |   |  - 算盘大师傅: Cube                |
|  - 钳工二师傅: Vector (算向量，极快)  |   |  - 钳工二师傅: Vector              |
+------------------------------------+   +------------------------------------+
                         ▲                         ▲
                         └───────────┬─────────────┘
                                     ▼
                    [楼道共享置物架: L2 Cache (问题三引入)]
                    - 容量 1MB，只能放读取的数据，先进先出(FIFO)
                    - 旁边配了专用快速直达电梯（250 字节/周期带宽，与公路完全独立）
```

- **我们要算的东西（计算图）**：就像一张复杂的流水线工序单，上面有几千上万个工序节点（算乘法、算加法）和成千上万个零件块（张量 Tensor）。
- **我们要交的答案（决策输出）**：
  1. **切成几份工序包**（`node_to_subgraph`）：把哪些算式打包成同一个子图。
  2. **哪个工位做哪个包、按什么顺序做**（`core_schedules`）：例如让工位 0 依次做子图 0、子图 2；工位 1 做子图 1。
- **评委的裁判程序在干嘛**：
  你交出上面两个字典后，官方程序会启动仿真模拟器：按你的划分检查有没有死锁、按数据流补齐搬运指令、看看工人桌面有没有被零件堆爆（爆了就会自动把零件扔回大仓库，要用再搬回来，这叫 **Spill 换入换出**），然后多核同时跑，看谁家**完工总时间（Makespan）最短**、**大公路上的额外运货量（Added Copy Bytes）最少**。

## 4. 三道赛题的“人话”机制深度拆解

### 4.1 问题一：场景 A —— 算清搬运账，让并行赚的周期大于搬运赔的周期

#### 核心物理现实
场景 A 中，NPU 的每个核心干完一个子图后，**桌面被强制清空（Cache flush）**。
- 如果工位 0 算出了张量 $z$，工位 1 接着要用 $z$，那么：工位 0 必须先把 $z$ 运回远郊大仓库（COPY_OUT），工位 1 再从大仓库运上自己的桌面（COPY_IN）。
- 就算工位 0 接下来要做的子图刚好也要用 $z$，对不起，因为属于两个不同的 Task，工位 0 必须先运回大仓库，再运回自己的工位！
- 此外，同核前后两个任务切换要罚坐 $100$ 个周期；跨核等前序任务完成要罚坐 $1000$ 个周期。

#### 核心数学公式的人话翻译
原版公式（3）：
$$Q_A^0 = \sum_{t\in T_{\mathrm{in}}} b_t |I_A(t)| + \sum_{t\in T_{\mathrm{prod}}} b_t \left[ |R_A(t)| + \mathbf1\{|R_A(t)|>0 \text{ 或 } o_t=1\} \right]$$

**人话翻译**：
1. **第一项（原材料采购）**：整个图需要的初始输入张量，被切分到了几个不同的子图，就得老老实实从大仓库读取几次（$b_t \times$ 接收子图数量）。
2. **第二项（中间半成品中转）**：算出来的中间张量，只要跨出了当前子图：
   - 目标子图有几个，就读几次（$|R_A(t)|$ 次）；
   - 当前子图自己必须往大仓库写一次（$+1$ 次）；
   - 如果这个零件本身就是最终需要交差的输出产品（$o_t=1$），那正好借着这次写出顺便交差，不重复计费。

#### 我们的切图哲学
切得越碎 $\to$ 多个工位可以同时干活（算盘和钳工利用率高） $\to$ 但大公路运费暴涨、交接等待时间（100/1000 cycles）暴涨。  
**结论**：绝不能无脑细切！优先把天然没有交集、互相独立的计算分支分给不同核（分量装箱）；在必须切的长依赖链上，只沿关键路径切大块（$2K \sim 4K$ 块），让“并行省下的时间”稳稳超过“运费和等待的损失”。

### 4.2 问题二：场景 B —— 同核复用与桌面防爆，调序消灭换入换出

#### 核心物理现实
场景 B 打开了核心间通信机制，平台进化了：
1. **同核数据复用**：同一个工位（Core）上的所有子图打包成一个大任务！上一个子图算完的数据，可以稳稳留在 L1/UB 桌面上，下一个子图直接拿来用，**一次大仓库都不用跑**（$C_{\text{inner}} = 0$）。
2. **跨核传输优化**：源核心写回 DDR，发一个信号等待 $500$ 周期，目标核就能去 DDR 读了。

原版公式（5）：
$$Q_B^0 = \sum_{t\in T_{\mathrm{in}}} b_t |I_B(t)| + \sum_{t\in T_{\mathrm{prod}}} b_t \bigl[2|R_B(t)| + o_t\bigr]$$
注意这里所有的接收集合下标都变成了 $B$（按**核心**统计，而不是按子图统计）。也就是说：**不管同一核心内切了多少个子图，只要不出这个核心，搬运费就是 0！**

#### 致命陷阱：桌子堆爆了（Spill 噩梦）
既然同核不收搬运费，那把所有强相关的算子全塞给同一个核不就行了？
**大错特错！因为桌面极其狭小（L1 只有 512KB，UB 只有 128KB）！**
- 如果你把一堆算子排在同一个核上，某个 400KB 的大张量很早被生产出来，但很晚才被用完，它就会一直赖在桌面上不走。
- 后面的算子一进来，发现桌子放不下了，官方的 `schedule_step2.py` 就会触发强制换出：**硬生生把这个大张量运去远郊大仓库，等要用的时候再从大仓库运回来！**
- 这一出一进，凭空产生了巨大的额外搬运量 $Q^{\mathrm{spill}}$，把原本好不容易省下来的 DDR 带宽彻底堵死。

#### 我们的解法：R序优先释放 + 容量代表拯救
1. **R序（Release-first 优先释放顺序）**：
   排定同核计算顺序时，只要某个零件在这个操作用完后就可以被丢弃释放，就立刻优先安排这个操作！**尽快腾出桌面**。
2. **容量代表（Capacity Candidate）**：
   在局部搜索时，哪怕一个方案的理论算力并行时间稍微长了一点点，但只要它让**“桌面峰值堆放量（$\Pi(X)$）”大幅下降**，我们就立刻把它单独提拔进候选池进行完整评估。实测表明：少一次桌面溢出，省下的 60B/cycle 传输时间足以拉开巨大优势！

### 4.3 问题三：场景 C —— 共享货架（L2 Cache）的时序对齐与错峰消费

#### 核心物理现实
场景 C 在场景 B 基础上，在车间走廊里加装了一个 **1MB 的只读置物架（L2 Cache）**，并且有一部专属快速货梯（带宽 250 字节/周期，走公路是 60 字节/周期）：
- **规则 1**：当工位需要从远方读取零件时，先看置物架上有没有。如果有（Hit），坐快速电梯（250B/cycle），不占用大公路；
- **规则 2**：如果置物架上没有（Miss），走大公路从远郊大仓库拉（60B/cycle）；
- **规则 3（极度关键）**：**货物只有在彻底搬运完成后，才会放上置物架！并且容量超 1MB 时按先进先出（FIFO）丢弃最老的货物。**

#### 致命的时序陷阱：为什么大家都在读，却总是 Miss？
看下面这个极为生动的例子：
> 核心 0 和核心 1 都需要用一份 60KB 的初始输入 $x$。  
> **情况 A（同时启动）**：时刻 0，核心 0 和核心 1 同时发起读取。此时置物架是空的，**两者全部 Miss**！两辆货车同时挤上 60B/cycle 的公路，各耗时 2000 周期才运完。置物架完全没发挥作用！  
> **情况 B（巧妙错峰）**：核心 0 在时刻 0 发起读取，用时 1000 周期运完，在时刻 1000 将 $x$ 稳稳摆上了置物架。核心 1 调整了核内子图顺序，先算了点别的，恰好在时刻 1000 发起对 $x$ 的读取——**瞬间命中（Hit）！** 走 250B/cycle 的专属电梯，仅需 240 周期就拿到数据！

#### 我们的三大调度手腕
1. **消费者聚合（Aggregation）**：
   对于超大张量（大于 1MB 的根本装不进 Cache），或者重复读取次数少的数据，直接把相关算子挪到同一个核心上，从根源上避免第二次读取。
2. **消费者分散（Dispersion）**：
   对于小于 1MB 且频繁被多个分支读取的张量，大胆把计算分散到多个核心，充分榨干 250B/cycle 的高速 Cache 带宽，换取多核强并行。
3. **时序微调（Timing Alignment）**：
   直接读取官方初次运行的 `cache_events` 日志，精准抓出那些“明明能复用、却由于排期太靠近导致连续 Miss”的倒霉张量。把后者的算子执行时机往后移一个节拍，实现 **100% 满血命中**。

## 5. 我们的算法求解器到底是怎么跑起来的？（三层加速体系）

搜索几千个算子的最优排布是一个 NP-hard 难题，如果每次稍微改动一个算子都去调官方模拟器，跑完全部 100 个用例需要几十天。我们设计了**“快筛、精检、终审”三层漏斗体系**：

```
+-------------------------------------------------------------------------------+
| 【第一层：速算估分板 (Lightweight Scoring)】（纳秒级）                          |
| - 不展开复杂的核内四流水线，直接在简化的拓扑骨架上快速递推最长路 H_light          |
| - 快速累加 DDR 独占搬运量 W_D、Cache 独占搬运量 W_L 与桌面溢出惩罚 live_bytes    |
| - 职责：一秒钟测试上万个局部小修改（迁核、拆并、调序），挑出前几十个最优秀的苗子 |
+-------------------------------------------------------------------------------+
                                        │
                                        ▼ 优胜劣汰
+-------------------------------------------------------------------------------+

```

### 四个高质量起跑线（Seeds）
为了防止搜索陷入死胡同，算法对每张计算图都准备了四个物理含义完全不同的起点：
- **种子 0（整图单核基准）**：不切分，全放单核，零跨核开销。
- **种子 1（分量天然装箱）**：把图里原本就没连在一起的弱连通计算分量，当成独立积木分装到各核心（零新增跨核切割，天然并行）。
- **种子 2（深挖支路并行的 D 序切块）**：沿深度优先分支切出 $2K$ 块，为大分支之间创造并行。
- **种子 3（保命长依赖链的 H 序切块）**：先算关键路径（最长依赖链）上的算子，围绕长骨架向外细分，切出细粒度子图。

## 6. 用一个极简微图把三问公式彻底算透

这里用第 7 节的手算示例，展示我们在草稿纸上也能算明白的硬核数学过程。

### 6.1 迷你零件加工单
```
输入数据 x (60,000 bytes)
   │
   ├───────┬────────────────────────┐
   ▼       ▼                        ▼
工序 p    工序 a                   工序 b
(用时1000) (用时800, 需要x和z)      (用时800, 需要x和z)
   │       │                        │
产出 z     产出 ya (6,000 bytes)    产出 yb (6,000 bytes)
(30,000)   │                        │
   ├───────┴────────┐               │
   ▼                ▼               ▼
 (给 a)           (给 b)          (存大仓库)
```
- 原始图数据运费（不可避免的底费）：搬入 $x$（60,000）+ 搬出最终成品 $ya, yb$（$6,000 + 6,000$）= **72,000 字节**。

### 6.2 方案比较大比拼

#### 方案 1：全放在同一个核心 0 上
- **问题一（A）搬运**：72,000 字节（全在一个子图，无额外搬运）。
- **问题二（B）搬运**：72,000 字节。
- **总计算耗时**：$1000 (p) + 800 (a) + 800 (b) = 2600$ 周期。没有并行。

#### 方案 2：将 $p, a, b$ 切成 3 个子图，分给 3 个核心同时干
- **问题一（A）搬运**：
  - 输入 $x$ 被三个不同子图使用，读 3 次：$3 \times 60,000 = 180,000$；
  - 中间件 $z$ 生产出来后，被两个外核使用，写 1 次、读 2 次：$3 \times 30,000 = 90,000$；
  - 最终成品写出：$12,000$；
  - **总运费**：$180,000 + 90,000 + 12,000 =$ **282,000 字节**（暴涨近 4 倍！）。
- **问题二（B）搬运**：
  - 3 个子图恰好在 3 个不同核心，输入 $x$ 进 3 个核心读 3 次：$180,000$；
  - 跨核传输：对每个目标核生成一对 COPY_OUT/COPY_IN：$2 \times 2 \times 30,000 = 120,000$；
  - 最终成品：$12,000$；
  - **总运费**：$180,000 + 120,000 + 12,000 =$ **312,000 字节**。
- **并行收益**：$a$ 和 $b$ 在不同核心上同时算，纯计算依赖链耗时从 2600 压缩到了 $1000 + 800 = 1800$ 周期。
- **决策结论**：虽然计算省了 800 周期，但在 60B/cycle 带宽下，多搬运 $240,000$ 字节需要消耗整整 **4000 个时钟周期**！这种细切完全是“得不偿失的亏本买卖”。

#### 方案 3：精明调度 —— $p$ 在核心 0，$a$ 和 $b$ 聚合在核心 1
- **问题二（B）搬运**：
  - 输入 $x$ 只进入两个核，读 2 次：$120,000$；
  - 中间件 $z$ 只向核心 1 发送一次：$2 \times 30,000 = 60,000$；
  - 最终成品：$12,000$；
  - **总运费**：$120,000 + 60,000 + 12,000 =$ **192,000 字节**（比 3 核方案立刻省下 120,000 字节！）。

#### 方案 4：问题三引入 Cache 后的神仙操作
在方案 2（三核并行）下，如果给输入 $x$ 加上 250B/cycle 的 L2 Cache：
- 核心 0 先读 $x$，耗时 $60,000 / 60 = 1000$ 周期；
- 核心 1 和核心 2 在时刻 1000 之后查询 $x$，**全部命中 Cache**！
- 核心 1、2 走专属电梯，耗时从 1000 周期骤降至 $60,000 / 250 = 240$ 周期；
- 结论：**硬件 Cache 使得方案 2 重新具备了极高的竞争力**！这就是问题三调度器会主动采取的“分散提速”机制。

## 7. 论文初稿写作模板与评委答辩绝杀话术

### ① 论文摘要核心段落模板（可直接自选用）
> 多核神经网络处理器调度是权衡计算流水并行度、片上私有缓存容量与共享访存带宽的复杂组合优化问题。针对现有切图策略中通信代价模糊、缓存溢出不可控及多核共享时序难对齐的挑战，本文提出了一种**张量驻留与查询时序驱动的多核调度优化模型与算法**。首先，基于张量生产者-消费者拓扑建立了统一的“张量驻留域”模型，推导出场景 A（Task 级）与场景 B（Core 级）的精确结构搬运量计算公式，解决了切图与通信代价脱节的难题；其次，在核内调度层面提出了关键路径与空间释放权衡的拓扑序列构造法，引入“活跃容量压力扫描”与“容量代表”，通过缩短长生命周期张量的重叠时间，显著抑制了片上 L1/UB 缓存的额外换入换出（Spill）；针对场景 C 共享只读 L2 Cache 的时序敏感特性，构建了基于事件驱动的 FIFO 查询回放与微调机制，并形成了共享输入“消费者聚合-分散-时序对齐”的三向搜索策略。实验表明，本方法在 100 张全量测试图上均能在合理时间内稳定收敛，方案全面通过官方评估器校验，在加速比与额外搬运量指标上均显著优于传统启发式基线。

### ② 答辩现场面对评委高频提问的“绝杀话术”

- **评委问**：“很多模型都用整图单核做基准，你们的加速比为什么有时候超过核心数，有时候又提升不明显？”
  - **绝杀回答**：“感谢评委老师的敏锐观察。这恰恰揭示了真实硬件的执行机制：第一，对于单核基准，官方采用的是固定启发式调度，在处理大图时由于 L1/UB 空间狭小产生了大量被迫的换入换出（Spill）；而我们在多核调度中，一方面分担了计算，更重要的是**把数据分散后大幅消除了单核的 Spill 搬运**，因而某些用例表现出超线性加速；第二，对于部分提升受限的用例，我们通过反向最长路径（下界分析）证明了其主要瓶颈受限于不可拆解的串行关键路径（$L_G$）或 DDR 60B/cycle 的固有带宽墙，我们的理论下界分析清晰地解释了各类计算图的物理性能边界。”

- **评委问**：“你们如何保证你们找出来的方案在官方评测程序里绝对不会死锁、不会超出缓存报错？”
  - **绝杀回答**：“我们在算法内部设计了‘三层漏斗评分机制’。第一层用轻量数学骨架毫秒级过滤无效状态；第二层直接对接官方提供的 `schedule_step1/2/3` 进行真实验证，完全继承官方的依赖检查与 Spill 插入逻辑；最后只将最具潜力的合格解交由多核仿真器判定。我们所有的调度方案在生成瞬间就已经百分之百符合无环 DAG 和物理缓存约束，不存在任何合规性风险。”
