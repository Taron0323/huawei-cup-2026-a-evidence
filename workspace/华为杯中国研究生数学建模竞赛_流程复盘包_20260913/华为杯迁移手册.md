# 华为杯中国研究生数学建模竞赛流程适配说明

版本：2026-09-13  
用途：把本次 C 题形成的工作方法整理为下一次华为杯中国研究生数学建模竞赛的可复用流程。

## 1. 适配原则

本文件总结的是工作方法、文件组织和核验习惯，不把本次 CUMCM 题面的规则、时间、页数、文件名或 AI 要求直接套用到华为杯。华为杯每一届的竞赛通知、题面、报名系统和提交页面可能改变，正式参赛前必须以当年研究生数学建模竞赛组委会发布的通知和系统提示为准。

本次 C 题的结果、论文和支撑包可以作为训练样例。下一次正式比赛应重新建立题面入口、需求表、数据清单、结果目录和交付状态；历史文件只能作为参考，不得将历史数值写入新题答案。

## 2. 可以直接复用的工作链

### 阶段一：接收题面并建立事实入口

1. 保存官方题面 PDF、全部附件和收到时间，原文件只读保存。
2. 建立 `REQ.md` 与 `requirements.csv`，逐条记录题面要求、页码、附件、输出形式和稳定编号。
3. 建立 `CONTEXT.md`，区分题面原句、数据事实、队伍决定、解释性假设和待核验事项。
4. 建立 `STATUS.md` 与 `HANDOFF.md`，记录当前阶段、已完成工作、未决问题和下一条可执行命令。
5. 第一轮只做题面理解和数据盘点，不急于写漂亮文字或生成最终图。

这一阶段在华为杯中仍然适用；题面目录、系统要求和文件命名应以当年通知覆盖。

### 阶段二：选题和风险判断

对每道题记录：数据是否完整、输出是否明确、关键数学结构、最小可行试跑、队伍已有能力、预计运行时间、最大失败风险和备用路线。先确认能否形成可核验的完整答案，再比较模型复杂度和展示空间。不要把主观喜好写成获奖概率。

如果题面存在歧义，记录原文、建议解释、受影响的问题和替代解释。核心目标函数、边界条件或正式结论尚未确定时，应保留决策记录，不能在正文里默改。

### 阶段三：数据体检与数量级预估

对每个输入表检查列名、单位、时间粒度、日期连续性、缺失值、重复记录、异常值和总量关系。先做数量级估算，例如总能量、总费用、样本量、误差范围或守恒量，再开始完整运行。清洗结果写入独立的 `clean/` 目录，原始附件不覆盖。

预测任务按时间切分训练和评估数据，预处理参数只在训练部分拟合。每个派生量保留来源列和计算公式，使论文表格、图形和代码能够回到同一结果文件。

### 阶段四：模型抽象和路线选择

先用自然语言说明变量之间的物理或业务关系，再写目标函数和约束。保留一个简单、可解释、能快速运行的基线模型；复杂算法必须说明它解决的具体困难、输入输出和退出条件。模型名称使用评委容易理解的功能性名称，例如“购电费用最小化线性规划模型”“岭回归负荷预测模型”“动态调整模型”，避免为普通步骤堆叠生造名词。

每个问题建立独立的模型卡，至少包括：输入、决策变量、目标、约束、参数来源、求解器、输出文件、适用范围和失败处理。问题之间的继承关系要写清楚，后一问若更换目标或信息条件，必须同步更新方法、公式、代码和正文。

### 阶段五：实现和可复现运行

代码按“数据读取—预处理—模型求解—结果导出—核验—绘图”分开。每次正式运行固定输入版本、参数、随机种子、运行环境和输出目录。输出至少包括 CSV/JSON 结果、参数清单、运行元数据和验证报告。

建议保留一个统一入口，例如 `support.py` 或 `run_all.py`，但入口应调用真实代码，不要用静态示例文件伪装重算。相对路径应以项目根目录为基准，避免换电脑后依赖个人绝对路径。运行前先做小规模试跑，确认维度、单位和约束，再做全年或全样本计算。

### 阶段六：结果核验

本次 C 题采用的六类检查值得保留：

- 量纲、数量级和边界退化检查；
- 小规模枚举或对拍；
- 独立实现或独立公式互验；
- 守恒关系、约束满足和题面示例对账；
- 结果表、图、正文数字一致性检查；
- 参数敏感性、重复运行波动和现实合理性检查。

核验通过只说明代码和数据在给定条件下满足检查，不能写成全局最优、真实部署效果或正式获奖保证。随机算法要登记种子并报告波动；启发式算法不写“保证全局最优”，除非有相应证明或穷举范围。

### 阶段七：图表与论文

先给每张图和表安排论证任务，再绘制。图表必须读取最终结果文件，不能手工改数字。曲线图统一字体、字号、线宽、图例和单位；不确定性带只有在有真实重复试验、标准差、标准误或置信区间时才绘制，不能为了美观虚构范围。每张图、表在正文中先有文字引出，再放图表，再解释关键变化。

论文写作沿用本次较有效的顺序：问题重述、符号与假设、数据预处理、模型建立、求解与结果、检验、评价与推广、参考文献、附录。正文语言以清楚说明“用什么数据、建立什么模型、怎样求解、得到什么结果”为主，少用空泛的套话、疑问句和防御性表述。最终 PDF 既要做文字抽取检查，也要逐页渲染检查图表、表格、分页、空白和公式。

### 阶段八：支撑材料和人工审阅

支撑材料应能回答三个问题：答案中的数字从哪里来、模型如何重跑、结果如何核对。建议包括：

- 与正文完全一致的结果 Excel；
- 运行入口、依赖文件和必要源代码；
- 题面附件及其来源说明；
- 结果 CSV/JSON、参数和图表数据；
- 核验脚本与核验报告；
- 当年要求的 AI 使用详情或其他声明文件；
- 简明的目录和运行说明。

本次 C 题采用“提交用轻量包”和“完整本地归档”两层结构。下一次是否需要 Excel、代码、AI 详情、日志或其他附件，必须以当年华为杯官方通知和提交系统为准。人工审阅状态单独记录，不用程序通过替代人工确认。

## 3. 必须重新核验的华为杯规则

下列内容不能从本次 CUMCM 经验直接推断，赛前应逐项打开当年官方来源并保存证据：

| 项目 | 需要核验的内容 |
| --- | --- |
| 参赛资格 | 研究生身份、导师或队伍要求、跨校组队限制、报名材料和截止时间 |
| 竞赛时间 | 题面发布时间、答题时长、提交开始与截止时间、逾期处理 |
| 题面与附件 | 题目发布渠道、附件格式、是否允许外部数据、数据使用范围 |
| 论文格式 | 模板、纸张、正文页数、摘要限制、字体、图表和公式要求 |
| 文件清单 | 主论文、支撑材料、源代码、Excel、说明文件、命名和压缩层级 |
| 文件大小 | 单文件及压缩包上限、是否允许多个压缩包、平台校验规则 |
| AI 使用 | 是否允许使用、是否必须声明、声明位置、使用详情格式和内容 |
| 匿名与署名 | 论文是否匿名、队伍信息放置位置、文件属性和路径是否需要清理 |
| 提交平台 | 上传账户、提交人、系统登录、回执和撤回/替换规则 |
| 赛区或学校通知 | 学校内部截止、区域要求和与全国通知的优先级 |

上述事项未核验前，状态应写成“待官方通知确认”，不能写“符合华为杯要求”。

## 4. 推荐的下一次目录

```text
华为杯数学建模-年份/
├── README.md
├── AGENTS.md
├── config/
│   ├── competition.json
│   └── official_sources.json
├── paper/
│   ├── inputs/              # 官方题面和附件，只读副本
│   ├── data/                # 原始数据，只读
│   ├── clean/               # 清洗和派生数据
│   ├── code/                # 求解、验证、绘图代码
│   ├── results/runs/        # 每次正式运行独立目录
│   ├── evidence/            # claims、图表、来源和核验关系
│   ├── latex/               # 论文主源
│   ├── figures/             # 图源和导出文件
│   ├── STATUS.md
│   ├── CONTEXT.md
│   ├── IDEA.md
│   ├── REQ.md
│   └── HANDOFF.md
├── Each Stage Review Work/  # 每次大编辑完整前后快照
├── support-package/         # 交付前临时组包目录
└── output/                  # PDF、ZIP 和人工审阅副本
```

每次大编辑在 `Each Stage Review Work/YYYYMMDD-NN-主题/` 留存修改前完整文件、修改后完整文件、差异、验证命令和实际结果。已交付快照不覆盖；新增、删除和未采用候选均登记。

## 5. 建议的时间安排

比赛开始后先用少量时间锁定题面、附件和题目分工，再安排一个短试跑判断路线。模型结构稳定后并行推进代码、验证和论文骨架；不要等全部实验结束才开始写章节。最后阶段只做证据驱动的修复：重新计算、修图、改正文或重排版都必须回到同一结果版本，并留出完整 PDF 渲染和压缩包解压检查时间。

具体时长应根据当年竞赛答题窗口调整。华为杯通知若给出明确节点，应覆盖本段的内部时间表。

## 6. 可直接复用的开工提示词

```text
请先读取项目 README、AGENTS、官方题面、全部附件和当年华为杯官方竞赛通知。
先建立 REQ.md、requirements.csv、CONTEXT.md、STATUS.md 和输入清单，原始题面与附件只读保存。
把题面原句、数据事实、解释性假设、队伍决定和待官方核验事项分开记录。
完成数据体检、数量级预估和最小试跑后，再为每一问给出模型卡：变量、目标、约束、参数来源、求解器、输出和验证。
所有数字必须来自当前运行目录；代码、结果、图、表和正文使用同一结果版本。
执行量纲、边界、小规模对拍、独立互验、守恒、敏感性和正文一致性检查。
论文按清晰的竞赛论文结构撰写，图表先在正文中引出并在下方解释，禁止虚构数据、引用、置信区间和官方要求。
在打包前重新打开当年官方通知，核对页数、文件名、AI声明、支撑材料、匿名和大小限制。
每次大编辑完整留档到 Each Stage Review Work；人工审阅、正式上传和外部服务器核验保持真实状态。
```

## 7. 本次 C 题经验的边界

本次项目验证了“334 天连续运行、五个结果工作簿、代码与结果互核、图表和正文统一、提交包解压复核”这一套证据链。它说明流程可以迁移，不说明下一次题目仍然需要相同的天数、Excel 数量、模型形式、页数或文件名。下一场比赛应重新做题面拆解和规则核验，再决定模型与交付范围。

本文件是流程适配建议，不是华为杯当年官方规则，也不代替队伍对报名、组队、论文、AI声明和最终上传的人工确认。
